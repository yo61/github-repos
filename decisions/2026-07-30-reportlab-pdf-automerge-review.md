## Decision: Land Dependabot updates on `claude-plugin-reportlab-pdf` unattended by requiring one approving review (supplied by the `yo61-lastlight` GitHub App) plus green required status checks, with native auto-merge. Express the CI gate as an in-code `additional_rulesets` "Required status checks" ruleset (the go-udap convention), add a repo-admin bypass for the review rule, and delete the hand-made `main branch protection` ruleset drift.

## Context: The `yo61-lastlight` GitHub App (id 4367919) vets Dependabot PRs but could not land them — repo auto-merge was disabled and there was no review-gated auto-merge path, so it posted a comment saying a maintainer had to merge manually (PR #18). Investigation found two overlapping default-branch rulesets: a Terraform-managed `Default Branch` (required_signatures + `semantic-release-pusher` bypass, no CI checks) and a hand-created `main branch protection` (required_status_checks for `Conventional Commits` + `plugin.json validation`, no bypass). The latter predated this Terraform system, existed only as untracked drift, and held the *sole* copy of the required status checks. lastlight's install has Contents + Pull requests read/write, so its approval counts as a required review and it can complete the merge.

## Alternatives considered:
- GitHub-native Dependabot auto-merge via a workflow using `GITHUB_TOKEN`, dropping lastlight from the loop — rejected: Robin wants lastlight as the vetting/approving actor, and going through the review keeps an auditable per-PR approval trail.
- Grant lastlight standing write and have it force-merge directly — rejected: no enforced gate; "no random PR lands" would rely on agent behaviour, not GitHub.
- Fold the CI checks into the built-in `default_branch` ruleset (one ruleset) via a module change — rejected: ruleset bypass is per-ruleset, all-or-nothing, so `semantic-release-pusher` would then also bypass CI. A separate, no-bypass status-checks ruleset is the only way to keep the release app subject to CI while exempt from signatures.
- Import the drifted `main branch protection` ruleset into state — rejected: it is differently named/shaped; cleaner to express the intent in code and delete the drift.

## Reasoning: The two-ruleset split is intentional and load-bearing — signatures-bypass for the release app, CI mandatory for everyone — and `go-udap.yaml` already encodes exactly this via `additional_rulesets`, so no module change is needed. `default_branch_ruleset_required_approving_review_count: 1` on the built-in ruleset is the "lastlight approved" clause; the no-bypass `Required status checks` ruleset is the "checks green" clause; `allow_auto_merge: true` merges the instant both hold. Random/human PRs get no lastlight approval → blocked by GitHub, not by trusting the agent. A repository-admin bypass (`RepositoryRole` id 5) on the built-in ruleset lets Robin merge his own PRs without a second approval while remaining bound by CI (the status-checks ruleset has no bypass).

## Trade-offs accepted: Two rulesets remain by design, now both declarative. lastlight holds Contents + PR write, so delegating the approve decision inherently grants merge capability — the branch protection is defense-in-depth, not a cage. The built-in ruleset's `dismiss_stale_reviews_on_push: true` can dismiss lastlight's approval on a Dependabot rebase and briefly stall auto-merge until re-approval; acceptable at this repo's update volume. The orphan `main branch protection` ruleset must be deleted out-of-band after apply, since it is not in Stategraph state.

## Supersedes: none.
