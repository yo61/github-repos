## Decision: Stop managing 164 of the 165 fork repos in Stategraph (keeping `kuard`, an actively-used fork) — remove their resources from state (without destroying them on GitHub), delete their `data/yo61/*.yaml` files, and scope drift-detection to non-fork repos. Then archive the pre-2019 forks on GitHub separately.

## Context: `github-repos` managed 191 repos, 165 of them forks (86%) — old public forks of other people's projects, mostly last pushed 2013–2018, with no custom config in their data files. They add noise to every plan and to the data directory while the maintainer only cares about the ~26 non-fork repos. The goal was to unmanage the forks (Terraform stops tracking them) while leaving them on GitHub.

## Alternatives considered:
- `removed` blocks with `lifecycle { destroy = false }` — rejected: Terraform rejects module **instance** keys in `removed` blocks ("Module address must be a module, not a module instance"), so individual for_each'd fork instances can't be targeted (verified at root and inside the module).
- `stategraph states export` → filter → `import` — rejected: `import` creates a **new** state (requires `--name`), it does not edit in place, so it would mean deleting the existing state and rebinding the workspace — convoluted and risky across 165 repos.
- Delete the data files and let Terraform destroy the forks — rejected: the maintainer wants the forks kept on GitHub.
- Archive-in-place instead of unmanaging (keep managed, `archived: true`) — rejected as the primary action: it declutters GitHub but leaves 165 data files under management. Retained as a complementary step for the old forks (see below).

## Reasoning: The maintainer added a gitignored `backend_override.tf` exposing the Stategraph state over Terraform's `http` backend, which makes the native `terraform` CLI (and `terraform state rm`) work against the same state. `terraform state rm module.org_yo61.module.repo["<fork>"]` forgets a resource without touching GitHub — the exact operation needed. Validated on one fork (`beets`: removed from state, still present on GitHub as a fork), with a full `terraform state pull` backup taken first. Then 164 forks were removed via `state rm` (515 instances) — `kuard` is kept as a managed exception because it is actively used — their 164 data files deleted, and the org module's drift-detection repointed from an all-repos query to the existing `fork:false` query so unmanaged forks are not flagged as drift. `terraform plan` afterwards reports "No changes" with no unmanaged-repo warnings — state and config agree on the 26 non-forks.

## Trade-offs accepted: The state was mutated out-of-band via the native CLI before the config change (deleted files) merged, so `main` and the live state briefly disagree until this PR merges; a `task apply` from old `main` in that window would try to recreate the forks and fail (repos already exist), not destroy them. State locking is not configured on the `http` backend (solo local use only). Re-managing a fork later is not a plain `terraform import`: the state records providers in Stategraph's `module.state_4da5d.provider[...]` form, which native import cannot reproduce (it would write a root-scoped provider and desync the state). `kuard` was instead re-established by splicing its resources out of the state backup into the current state and pushing (serial bump, matching lineage) — the format stays consistent. A `terraform state pull` backup is retained out-of-band as the restore path.

## Supersedes: none. Follows 2026-07-30-org-default-admin-bypass-non-fork.md — the same `fork:false` query now drives drift-detection as well as the bypass scope. The pre-2019 forks are archived on GitHub as a separate follow-up (a pure GitHub API operation, since the forks are no longer managed).
