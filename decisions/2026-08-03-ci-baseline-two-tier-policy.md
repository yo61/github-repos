## Decision: Standardise CI across the 13 recently-active managed repos as a two-tier policy. **Tier 1 (every repo):** a no-bypass `required_status_checks` ruleset enforcing `Conventional Commits` + `lint` (`prek run --all-files`) + a stack-appropriate validation/build/test, green before any merge. **Tier 2 (repos with a behavioural check):** additionally `allow_auto_merge: true` + the built-in `default_branch` ruleset at `required_approving_review_count: 1` (lastlight-supplied approval). A "behavioural check" is judged per repo by what it produces: a test suite for code, a `build` for a docs site, `claude plugin validate --strict` for a payload-free plugin, and a real test suite (not validation) for a plugin that wraps executable code.

## Context: Auditing the recently-active repos for this rollout found the CI itself, not just the gate config, was divergent — some repos had auto-merge enabled with no CI gate (`gh-release-stats`, `claude-skills`, `homebrew-tap`), two had no CI workflows at all (`civi-mcp`, `github-repos`), and the plugin repos validated their manifests with hand-rolled `jq` shape-checks. Robin's requirement: every repo must have a meaningful CI baseline (lint + validation + build as the bare minimum) that is green before merge, and auto-merge must not be enabled unless a check meaningfully exercises what the repo produces. This defines "meaningful" per repo rather than by a single rule — a green `next build` is the behavioural check for a docs site; `claude plugin validate --strict` is the maximal check for a plugin with no executable payload; a plugin wrapping Python code (`reportlab-pdf`) needs a real test suite because validation never runs the code.

## Alternatives considered:
- **Enforce identical workflow files across repos.** Rejected: the stacks are genuinely heterogeneous (Python/uv, TS/oxlint, Go, Next.js docs, HCL/Terraform), so identical files are impossible. What is standardised is the *contract* — the set of required check contexts and their names — with `prek run --all-files` as the one uniform `lint` entrypoint every repo already supports.
- **Treat lint + manifest-validation as sufficient for auto-merge everywhere.** Rejected: this is the `reportlab-pdf`/`claude-skills` case where auto-merge would land bot PRs on structural checks that never exercise behaviour. Tier 2 requires a behavioural check.
- **Require a `tests/` suite on every repo before auto-merge, uniformly.** Rejected as too blunt: it would deny auto-merge to a docs site whose `build` genuinely validates its output, and would demand meaningless unit tests on payload-free plugins. The per-repo "what does it produce" judgement is the point.
- **Include the dormant managed tail (2013–2017 Puppet/Vagrant/mcollective).** Deferred, not rejected: most have nothing meaningful to build or test and no active PRs; a separate decision.
- **Keep the hand-rolled `jq` manifest validation in the plugin repos.** Rejected: `claude plugin validate --strict` is first-party, headless, CI-ready, and validates more (marketplace duplicates, path traversal, skill frontmatter). Pending one verification — that `--strict` exits non-zero on failure — with a `jq`/schema fallback if not.

## Reasoning: The two tiers map cleanly onto the two rulesets the repo module already supports — the no-bypass status-checks ruleset is the universal "CI green" clause, and `allow_auto_merge` + the review count is the conditional "lastlight-vetted, auto-land" clause. Defining the behavioural bar per-repo (rather than "has a tests/ dir") matches how each repo actually fails: a docs site fails by not building, a metadata plugin fails by not validating, a code library fails by a broken test. `prek run --all-files` gives an identically-named `lint` check across every stack because every repo already ships a prek config, so the baseline is real without pretending a Terraform repo runs pytest.

## Trade-offs accepted:
- Per-repo YAML repeats the `additional_rulesets` block across ~11 files rather than defaulting once in `modules/org`; accepted because the check contexts are genuinely per-repo (carried over from the prior decision).
- Two repos (`civi-mcp`, `github-repos`) and one test suite (`reportlab-pdf`) need code changes in the *target* repo before their gate can be added here — handled as Phase 2, separate PRs.
- `homebrew-tap` cannot back a required-checks gate until it grows an always-run aggregator job (its CI is `paths:`-filtered, so a required check hangs on non-matching PRs); deferred.
- The two orphan `main branch protection` drift rulesets (`jobhound`, `contributory-factors`) must be deleted out-of-band after apply, since Stategraph does not manage them.
