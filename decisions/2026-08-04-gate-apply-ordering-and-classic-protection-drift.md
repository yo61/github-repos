## Decision: Two additions to the Tier-2 rollout procedure. **(a)** Treat *classic branch protection* as a second drift shape alongside drift rulesets: sweep for it with the GraphQL `branchProtectionRules` query (rulesets and classic protection are disjoint APIs — `gh api repos/<r>/rulesets` cannot see classic protection), promote any contexts it holds that are not already declared, then delete it out-of-band after apply. **(b)** Make "re-trigger lastlight on open, already-reviewed dependency PRs" an explicit post-apply step of every gate rollout: a PR reviewed while its repo lacked `allow_auto_merge` stays stranded after the gate goes live, because nothing revisits it.

## Context: `unifi-mcp` PRs #31/#32/#33 sat green, lastlight-approved, and unmerged. lastlight had commented at 2026-08-02T23:06–23:08 — *"safe to auto-merge, but auto-merge is disabled for this repository, so a maintainer needs to merge it manually"* — which was accurate at the time: the Phase-0 apply (`decisions/2026-08-03-ci-baseline-two-tier-policy.md`, plan Task 1) landed at 2026-08-03T12:55Z, roughly 14 hours later, having been stalled since 2026-08-02 by a Stategraph outage. Nothing revisited the PRs afterwards. lastlight's own `cron-dependabot-merge` daily backstop (14:00, `apps/server/workflows/cron-dependabot-merge.yaml`) did not recover them across the intervening window either, so the backstop cannot be assumed to close this gap.

Re-triggering works and is fast: a maintainer comment on #31 at 10:16:08Z produced a merge by `yo61-lastlight[bot]` at 10:16:47Z — 39 seconds. #32 landed the same way. #33 was declined because it carries a `requires-human` label; lastlight also, correctly, refused to accept an unverified comment as authorization to bypass that label. That is the gate behaving as designed, not a failure.

Separately, `unifi-mcp` carried a **classic branch protection** rule on `main` (creator `robinbowes`, `requiredApprovingReviewCount: 0`) listing six contexts: the three declared in `data/yo61/unifi-mcp.yaml` plus `zizmor`, `osv-scanner`, `sbom-scan`. GitHub enforces the union of classic protection and rulesets, so `main` was gated on six checks while its YAML declared three. The Phase-1 drift table tracks only *rulesets* (`jobhound` 16287941, `contributory-factors` 16547942 — both since deleted, Task 6 complete), and Task-1 Step-4's verification runs `gh api repos/<r>/rulesets`, which never returns classic protection. The rollout's own checks therefore cannot see this drift shape.

A GraphQL sweep of all 13 in-scope repos found exactly two carrying it:

| Repo | Classic protection contexts | Already in its ruleset? | Action |
| --- | --- | --- | --- |
| `unifi-mcp` | `check (node 22)`, `check (node 24)`, `Conventional Commits`, `zizmor`, `osv-scanner`, `sbom-scan` | 3 of 6 — the security checks are **not** declared | promote the 3, then delete |
| `claude-skills` | `Conventional Commits`, `Marketplace JSON validation`, `Check plugin source refs resolve` | all 3 (its ruleset also has `lint`) | fully redundant — delete, no config change |

The other eleven are clean.

## Alternatives considered:
- **Delete `unifi-mcp`'s classic protection without promoting its contexts.** Rejected: it would silently drop `zizmor`, `osv-scanner` and `sbom-scan` from the gate. All three run unconditionally on every PR (`ci.yaml`/`security.yaml` — no `paths:` filter, no event conditional), and `go-udap.yaml` already gates on the equivalent `govulncheck`/`sbom-scan`, so they belong in the declared gate rather than being quietly discarded.
- **Import the classic protection into Stategraph state.** Rejected for the same reason `decisions/2026-07-30-reportlab-pdf-automerge-review.md` rejected importing the reportlab drift ruleset: it is a differently-shaped resource. Express the intent in code, delete the drift.
- **Add a `dependabot-automerge.yaml` workflow to `unifi-mcp`.** Rejected — already rejected in the 2026-07-30 decision, which keeps lastlight as the vetting actor and preserves the per-PR approval trail. The stranded PRs were an ordering artifact, not a missing mechanism; adding a workflow would have papered over a procedure gap with redundant machinery.
- **Rely on lastlight's `cron-dependabot-merge` backstop instead of an explicit post-apply step.** Rejected as the sole remedy: it did not recover these three PRs. Why it did not is a lastlight-side question (the workflow is `pr_scoped: true` with per-head-SHA dedup, which would make a config change invisible to a PR already assessed at that SHA) and is tracked separately; the rollout procedure should not depend on it.
- **Extend the Task-1 Step-4 verification to assert on open PRs.** Deferred rather than rejected: worth doing, but the immediate need is that a human running the rollout knows to look. Encoded as a procedure step first.

## Reasoning: Both additions close gaps where a *green rollout verification coexists with a broken outcome*. Task-1 Step-4 passed on `unifi-mcp` — both rulesets present, `allow_auto_merge=true` — while three PRs sat stuck and `main` was enforced on twice the declared checks. A verification that only inspects repo config cannot detect either condition, because one lives in PR state and the other lives in an API the check does not query. Making the drift sweep use GraphQL and adding an explicit post-apply PR pass gives the rollout eyes on both. Promoting `unifi-mcp`'s security contexts rather than dropping them keeps the effective gate identical across the transition, so deleting the classic rule is a no-op for enforcement and purely a reduction in undeclared state.

## Trade-offs accepted:
- **The apply for this is blocked.** `task plan` fails with the documented Stategraph `/logs/append` 404 (`tx 06747cad`, tracked upstream at stategraph/releases#3) — the same class of outage that stalled Phase 0. The config change lands in code now; the gate widening and both drift deletions wait for Stategraph to recover. Until then `unifi-mcp`'s `main` stays enforced at six checks via the classic rule, which is the same effective gate — still undeclared, but not weaker.
- The post-apply re-trigger is a manual step. Automating it (a sweep that re-triggers lastlight on open bot PRs after an apply) is a follow-up, not this decision.
- `unifi-mcp` #33 remains open by design: it is labelled `requires-human`, so it needs a deliberate maintainer merge. The `requires-human` label is a lastlight-side gate independent of the config policy recorded here, and this decision does not change it.
- The sweep covered the 13 in-scope repos only. The dormant managed tail is untouched, consistent with the existing scope.
