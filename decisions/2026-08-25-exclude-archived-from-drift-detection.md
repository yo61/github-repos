## Decision: Narrow the `modules/org` drift-detection query from `org:<org> fork:false` to `org:<org> fork:false archived:false`, so archived repos are excluded from both the `unmanaged_repos` check and the non-fork admin-bypass set.

## Context: Archiving `python-template-archived` on 2026-08-25 (see `decisions/2026-08-25-python-template-recreate-to-drop-template-link.md`) left a repo on GitHub with no local config, so `check "unmanaged_repos"` reported it as a warning on every plan. That is standing noise of exactly the kind the same day's work was spent removing, and the check is the mechanism that tells the difference between a genuinely unmanaged repo and one deliberately frozen.

## Alternatives considered:
- **Give the archived repo a data file plus an `import` block.** Rejected as unworkable rather than merely fiddly: `modules/github-repo` manages `github_repository_collaborators` unconditionally, and a minimal file (`builtin_ruleset_names: []`) would plan to delete the two rulesets the repo still carries. GitHub rejects writes to archived repos, so those calls fail at apply time. Managing an archived repo is not something the module supports.
- **Leave the warning standing.** Rejected: a permanent warning trains the reader to skip warnings, which is how a real unmanaged repo would later go unnoticed.
- **Filter archived repos out in HCL after the query.** Rejected: `github_repositories` returns names only, so the module would need a second lookup per repo to learn archive status. The search API answers it in the same call.
- **Rename the data source and the `default_branch_ruleset_non_fork_bypass_actors` variable to match the narrower set.** Rejected for now: the variable is part of this module's public interface and renaming it is a breaking change for a cosmetic gain. The comment above the data source records that the set is narrower than the name suggests.

## Reasoning: An archived repo cannot be managed — GitHub rejects writes to it — so a data file could not be applied even if one existed, and an admin bypass on its ruleset would be inert. Excluding archived repos keeps `missing_configs` to repos that can actually be acted on, which is what the check is for. GitHub's search API supports `archived:false` directly, verified on 2026-08-25: `org:yo61 fork:false` returns 28, `archived:false` returns 27, and `archived:true` returns exactly `python-template-archived`. No hand-maintained flag is introduced, matching the reasoning in `decisions/2026-07-30-org-default-admin-bypass-non-fork.md` for reading fork status live.

## Trade-offs accepted: Archiving a managed repo out-of-band now silently drops it from drift detection instead of flagging it — acceptable, since an archived repo is frozen by definition and its config can no longer be applied. Its data file, if any, stays in `data/<org>/` and is still rendered by the module, so state and config keep agreeing; only the *reverse* check (GitHub repos lacking config) narrows. There were no archived non-fork repos in `yo61` before this change, so the blast radius on the day was zero.

## Supersedes: none. Extends `decisions/2026-07-30-unmanage-forks.md`, which repointed drift detection at the `fork:false` query; the same query now also excludes archived repos. Also extends `decisions/2026-07-30-org-default-admin-bypass-non-fork.md`, since the bypass scope is derived from the same data source.
