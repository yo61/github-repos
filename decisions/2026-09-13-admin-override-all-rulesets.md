## Decision: Give the repository Admin role (`RepositoryRole` id 5, `bypass_mode: always`) a bypass on **every** ruleset in **both** orgs — the built-in `default_branch` ruleset and every `required_status_checks` ruleset declared under `additional_rulesets` — and drop `default_branch_ruleset_required_approving_review_count` to the module default of `0` on all fifteen repos that set it to `1`.

The admin bypass moves from `default_branch_ruleset_non_fork_bypass_actors` to the plain `default_branch_ruleset_bypass_actors`, so it no longer skips forks, and that now-unused variable is deleted. A new `additional_ruleset_bypass_actors` variable carries the same default onto user-supplied rulesets, declared once in `main.tf` rather than restated in fifteen data files.

## Context: lastlight has been switched off to save money. It was the fleet's only approver, and fifteen repos required one approving review.

`CLAUDE.md` already documented the half-failure: from somewhere between 2026-07-30 and 2026-08-11, lastlight's router stopped sending dependency PRs down the path that approves, leaving 26 open Dependabot PRs `MERGEABLE` with every check green, auto-merge armed on 21, and `reviews=0` on all 26. That was a regression with a plausible fix in `yo61/lastlight`. Turning lastlight off entirely removes the fix: there is now no mechanism, regressed or otherwise, that can satisfy `required_approving_review_count: 1` on any repo. Every PR on those fifteen repos is unmergeable except by override.

One fact decided the shape of the fix. **A bypass actor does not satisfy GitHub's auto-merge.** This repo already proved it empirically: after the apply that set `allow_auto_merge: true` on `claude-plugin-reportlab-pdf`, its four open Dependabot PRs were re-armed per `2026-08-10-post-apply-pr-reevaluation` and all four stayed `BLOCKED` at `reviews=0` — with the org-wide admin bypass already in place since 2026-07-30. Bypass lets a maintainer click merge; it does not let GitHub merge on their behalf. So a bypass alone would leave every bot PR needing a manual click forever, which is the friction this is meant to remove.

## Alternatives considered:

- **Add the bypass, keep `required_approving_review_count: 1`.** Rejected on both halves. It does not restore auto-merge, per the evidence above, so bot PRs still need a manual click each time. And with no approver left, the rule would be satisfied by override on literally every merge — precisely the failure `2026-08-06-unifi-mcp-ci-only-gate` named: *"a control that is always overridden trains you to override it."*
- **Drop the review counts, add no bypass.** This is exactly the posture `2026-08-06` chose for `unifi-mcp`, and it is the smaller change. Rejected because it leaves no override path at all: a red or stuck required check blocks the maintainer with no way through except editing Terraform and applying. The whole point of the request was an override.
- **Restore lastlight's approval on the dependency path.** The fix `CLAUDE.md` argued for, and the right one while lastlight was running. Moot: lastlight is off by choice, for cost. Reviving a paid service to satisfy a rule is the tail wagging the dog.
- **Declare `bypass_actors` per repo in the fifteen data files.** Rejected for the same reason `2026-07-30-org-default-admin-bypass-non-fork` rejected it: restating one actor fifteen times invites drift, and the org module already has a working pattern for org-wide defaults.
- **`bypass_mode: pull_request` instead of `always`.** Tighter — it permits an override at merge time but still refuses a direct push to the default branch. Rejected for now only because the twenty-nine repos already carrying this bypass use `always`, and a fleet running two modes is harder to reason about than one. Worth revisiting as a single fleet-wide change rather than a split.

## Reasoning: With no approver, the honest choice is between a review rule nobody can satisfy and no review rule. `2026-08-06` already settled that question for `unifi-mcp` and gave the reason; what has changed is that its precondition — one repo losing its automated approver — now holds for all fifteen. Generalising its outcome is consistency, not a reversal.

What *is* a reversal is putting a bypass on the `required_status_checks` rulesets. `2026-08-06` deliberately kept those unbypassable and leaned on them as the half of the gate that binds everyone including admins. That reasoning was sound while a second control existed. It no longer does: with review counts at 0, CI is the only gate, and an ungated maintainer facing a stuck required check has no path forward but a Terraform change. Accepting an override on the last remaining control is a real cost, taken knowingly, in exchange for not being locked out of a repo by a check that will never turn green.

It also closes a bootstrap gap filed against an earlier PR and dismissed there as unfixable in a data file: *"New repos miss the admin bypass on the apply that creates them… the missing bypass comes from a first-apply ordering property of `modules/org` (the `non_fork` data source is read before the repos exist)."* The bypass no longer routes through that query — it is a static value on the module — so a repo created by an apply now carries the admin bypass from that same apply, with no second run needed.

Dropping the fork exclusion costs nothing. It existed to keep a large, noisy plan off 165 unmanaged forks; `2026-07-30-unmanage-forks` has since shrunk the managed set to three forks — `agent-team-topologies`, `commitlint-github-action`, `kuard` — so the query that scoped it is now scoping almost nothing. The `github_repositories` data source stays regardless: `check "unmanaged_repos"` still needs it.

`homebrew-tap` is the one repo that needs its bypass restated rather than inherited. Its `default_branch_ruleset_bypass_actors: []` (PR #25, 2026-07-14) was aimed at the semantic-release-pusher Integration actor, two weeks before the admin role became an org default — and because a per-repo list replaces the org default rather than extending it, that line silently swallowed the admin bypass too. It now names the admin role explicitly and still excludes the Integration actor, which is what PR #25 actually wanted.

Writing it out also **resolved a standing drift** that had gone unnoticed. `GET /repos/yo61/homebrew-tap/rulesets/16783297` returns exactly one bypass actor — `{actor_id: 5, RepositoryRole, always}` — while `terraform state show` for that ruleset had no `bypass_actors` at all. The admin bypass had been added out of band some time after PR #25 applied the empty list, and the config has been asking to remove it ever since. The new config matches live exactly, so the plan records the block as unchanged rather than added. Per the stale-side criterion in `quality/criteria.md`, live was the deliberate side here: it is the state this decision would have created anyway.

Deleting the `[]` line instead of replacing it would have looked equivalent and quietly reintroduced the Integration actor to a repo that had removed it on purpose.

## Trade-offs accepted:

- **CI is now overridable by an admin on all fifteen repos.** `osv-scanner`, `sbom-scan`, `secrets` and the rest still run and still report, and they still block everyone who is not a repo admin — including any outside contributor. But the maintainer can merge over a red check without touching Terraform. This is the control `2026-08-06` explicitly preserved, and it is being given up.
- **No human-approval requirement anywhere in the fleet.** Public repos now match the posture `2026-08-10-private-repos-manual-review-gate` described for private ones: CI is signal, a human decides. The difference is that on public repos CI *can* still block a non-admin, so the two are not identical.
- **The fleet's only remaining unbypassable protections are the `default_branch` rules** — `deletion`, `non_fast_forward`, `required_signatures` — and those carry `bypass_mode: always` for the admin too. In practice an admin is unconstrained on any managed repo. That is the plain consequence of the request and is stated here rather than discovered later.
- **`homebrew-tap`'s `default_branch_ruleset_dismiss_stale_reviews_on_push: false` becomes inert** — there is no required approval left to dismiss. Kept anyway, with its comment rewritten, so `2026-08-12-homebrew-tap-dismiss-stale-override` does not have to be rediscovered if a reviewer is ever reintroduced.
- **Re-enabling lastlight will not restore the gate by itself.** The review counts are gone from the data files, so bringing an approver back means putting them back too. That is deliberate — the two only make sense together, per `2026-08-06` — but nothing will prompt it.
- **On `ycst-org-uk`, the override will cover a second person.** `RepositoryRole` 5 is *whoever holds repo admin*, not a named user. All five `ycst-org-uk` repos grant `permission: admin` to the `admins` team, and `data/ycst-org-uk/_teams.yaml` lists `planetseth` as a member alongside `robinbowes`. This is inert today — those repos are private on the free tier and carry `builtin_ruleset_names: []`, so no ruleset exists to bypass — but the default is set on `module "org_ycst_org_uk"` and will apply the moment that org has a repo that can hold one. On `yo61` the question does not arise: `robinbowes` is the only admin grant in the data. Recorded because the symmetry that makes the two orgs read alike is also what makes this non-obvious.
- **A blocking quality criterion had to be rewritten.** `quality/criteria.md` carried *"The `required_status_checks` ruleset carries no bypass"* as a blocking check. It is amended by this decision rather than quietly violated.

## Supersedes:

- `2026-07-30-org-default-admin-bypass-non-fork.md` — fully. The bypass is unconditional; the fork-scoping variable it introduced is deleted.
- `2026-08-06-unifi-mcp-ci-only-gate.md` — in part. Its **outcome** (review count 0, CI as the gate) is generalised from one repo to all fifteen. Its **premise** (the status-checks ruleset must carry no bypass) is reversed, with the cost stated above.
- `2026-07-30-reportlab-pdf-automerge-review.md` and `2026-08-03-plugin-repos-review-gated-automerge.md` — in part. The auto-merge and two-tier CI baseline they established stand; the "review-gated" clause does not.

`2026-08-10-private-repos-manual-review-gate.md` is unaffected: the five `ycst-org-uk` repos and the private `yo61` ones still carry `builtin_ruleset_names: []`, so there is no ruleset to bypass. The bypass default is set on `module "org_ycst_org_uk"` for symmetry, and is inert until that org has a repo that can hold a ruleset.
