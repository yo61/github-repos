## Decision: Add a `topics` input to `modules/github-repo` that is **authoritative**: it defaults to `[]`, so a topic not named in a repo's data file is removed on the next apply. The twelve topics currently live on three `yo61` repos are imported into their data files in the same change. The type is `set(string)`, validated for GitHub's topic format and its limit of 20 per repo.

## Context: `github_repository` has always accepted `topics`, but the module never wired it, so a `topics:` key in a data file was silently dropped — `modules/org/main.tf` forwards only the keys it names and nothing validates unknown ones, the same trap `CLAUDE.md` records for a top-level `bypass_actors:`. Three `yo61` repos carry topics set outside Terraform: `lambda-copy-db-snapshot` (3), `claude-plugin-contributory-factors` (4) and `claude-plugin-reportlab-pdf` (5). No repo in `ycst-org-uk` has any. Any wiring of the attribute had to decide whether the data file or GitHub owns that state.

## Alternatives considered:
- **Default `null`, leaving topics unmanaged unless declared.** This was the first implementation and was rejected on review. The provider marks `topics` `optional: true, computed: true` (confirmed via `terraform providers schema -json`), so `null` means "leave alone, adopt what is live". It makes the change purely additive — an unscoped plan stays clean with no import work — but it leaves a hole in the declarative model: the twelve live topics would stay described by nothing, and a topic added or deleted in the UI would never be reported. That is precisely the drift this repository exists to eliminate.
- **Default `[]` without importing the live topics first.** Rejected as a silent destructive change. `[]` means "manage it, and it is empty", so the first apply would have deleted all twelve topics as an ordinary in-place update that reads like routine reconciliation. Verified rather than assumed: `topics: []` on `claude-plugin-reportlab-pdf` plans the deletion of all five of its topics.
- **`list(string)` instead of `set(string)`.** Rejected: GitHub treats topics as unordered, so a list makes reordering a key in YAML a spurious diff. The provider schema is a set.
- **No validation.** Rejected: the API rejects a malformed topic anyway, but at apply time and with a less specific message. Validating in the variable fails at plan time, and `modules/github-repo/variables.tf` already validates `visibility` and the merge-commit fields.

## Reasoning: Every other repo setting in this repository is declared, and the data file wins. Topics were the one attribute where GitHub would have kept quietly owning state, which makes `check "unmanaged_repos"`-style reasoning unavailable for them — you could not tell from the config what topics a repo has. Authoritative topics match the treatment already given to team membership, which `CLAUDE.md` documents as "a member added in the UI is removed on the next apply". The import is what makes `[]` safe, and its completeness is verifiable rather than asserted: after declaring the twelve topics, an unscoped `task plan` returns `No changes`. Had a single topic been missed, it would have appeared as a removal.

## Trade-offs accepted: Topics can no longer be managed from the GitHub UI — one added there is deleted on the next apply, exactly as with team membership. Adding a topic now means editing a data file and running an apply, which is slower than clicking, and someone who does not know that will lose their change silently. The compensating property is that the data files now describe topics completely, so the twelve that exist are reviewable in git rather than discoverable only through the API. `default = []` with `nullable = false` also means an explicit `topics: []` and an omitted key are identical, which removes the earlier hazard where the two differed.

## Supersedes: none.
