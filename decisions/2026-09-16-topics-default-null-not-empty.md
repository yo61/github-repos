## Decision: Add a `topics` input to `modules/github-repo`, defaulting to `null` (leave unmanaged) rather than `[]`, and forward it from `modules/org`. The type is `set(string)`, validated for GitHub's topic format and its limit of 20 per repo.

## Context: `github_repository` has always accepted `topics`, but the module never wired it, so a `topics:` key in a data file was silently dropped — `modules/org/main.tf` forwards only the keys it names and nothing validates unknown ones, the same trap `CLAUDE.md` records for a top-level `bypass_actors:`. Three `yo61` repos carry topics set outside Terraform: `lambda-copy-db-snapshot` (3), `claude-plugin-contributory-factors` (4) and `claude-plugin-reportlab-pdf` (5). Any wiring of the attribute had to decide what happens to those.

## Alternatives considered:
- **Default `[]`.** Rejected, and this is the whole point of the record. The provider marks `topics` `optional: true, computed: true` (confirmed via `terraform providers schema -json`). Under that combination `null` means "leave alone, adopt what is live" while `[]` means "manage it, and it is empty". A default of `[]` would therefore have planned the removal of all twelve live topics across the three repos on the next apply, as an ordinary in-place update that reads like routine reconciliation. Verified rather than assumed: setting `topics: []` on `claude-plugin-reportlab-pdf` plans the deletion of all five of its topics.
- **Default `[]` and immediately declare the live topics in those three data files.** Rejected as a bigger, riskier change than the one asked for. It converts a capability addition into a fleet-wide content migration, and any repo missed between merge and apply loses its topics silently.
- **`list(string)` instead of `set(string)`.** Rejected: GitHub treats topics as unordered, so a list makes reordering a key in YAML a spurious diff. The provider schema is a set.
- **No validation.** Rejected: the API rejects a malformed topic anyway, but at apply time and with a less specific message. Validating in the variable fails at plan time, and `modules/github-repo/variables.tf` already validates `visibility` and the merge-commit fields.

## Reasoning: `null` keeps the change additive. Adding the attribute with no data file declaring it is a no-op, confirmed by an unscoped `task plan` returning `No changes` against the whole fleet — so the three repos with out-of-band topics are untouched and nothing needs migrating in the same PR. Declaring `topics:` on a repo then works as expected: two valid topics on `horopter` plan as `0 to add, 1 to change, 0 to destroy`. This matches the null-means-unmanaged pattern the module already uses for `vulnerability_alerts` and `dependabot_security_updates`, which exists for the same reason — adding an attribute should not retroactively claim ownership of state the config has never described.

## Trade-offs accepted: The config is not the source of truth for topics on a repo that does not declare them, so the three repos above keep topics that no data file records, and drift detection will not notice if someone edits them in the UI. That is the deliberate cost of `null`, and it is reversible per repo: declare `topics:` on a file and that repo becomes authoritative from then on. The `[]` hazard also survives this decision — anyone writing `topics: []` meaning "I have no topics" will silently delete the repo's topics instead of leaving them alone. The variable description says so explicitly, in the words a reader will see in `modules/github-repo/README.md`.

## Supersedes: none.
